# NeoAG Web UI - conversational front end to the NeoAG neoantigen
# pipeline (MOCK PIPELINE DATA; real-agent chat behind an explicit
# mode switch)

Redesigned 2026-11-13 from a single-page mock prototype into a
conversational two-pane shell: the agent conversation is the primary
surface, the contextual workspace (Tasks / Results / Discovery / Help)
sits beside it. All pipeline data is synthetic and reproducible; the
chat can additionally reach the REAL server-side CodeBuddy agent,
behind an explicit, audited mode switch with named, honest limits.

**Nothing here touches the real pipeline, real data or patient data.**
Every sample ID is `DEMO-*`, every number is generated by a seeded RNG,
and every log line is marked `(mock)`. The real NeoAG repository, the
deployed pipeline, the CodeBuddy Web UI and the Cloudflare tunnel were
NOT modified by this project.

## Run it

```bash
cd /data1/neoag/agents/neoag-web-demo
./start.sh            # -> http://127.0.0.1:8712   (loopback only)
./stop.sh
```

The server runs detached under `watchdog.sh` (auto-restart; stop via
`./stop.sh`, which also creates `data/STOP` for the watchdog). Server
log and durable state: `data/server.log`, `data/state.sqlite3`.
Stack: Python 3 stdlib only (`ThreadingHTTPServer`, `sqlite3`) plus a
build-free vanilla-JS frontend. No packages installed anywhere.

## What the redesign changed (2026-11-13)

- **Two-pane shell**: agent conversation pane on the left, contextual
  workspace on the right. The old standalone Chat / Data / Audit /
  Discovery pages are gone; their useful content moved into workspace
  views or chat flows.
- **Conversational agent first**: quick actions, suggestions and the
  input-manifest review all surface in the chat; the workspace shows
  the formal artifacts (jobs, results, decisions, help).
- **One demo indicator** replaces the repeated per-message
  "MOCK PROTOTYPE" chat banners (legacy banner rows are purged at
  server start by a migration in `store.py`).
- **Code-grounded parameter inventory** (`backend/neoag_params.py`):
  every user-adjustable NeoAG parameter is derived from the frozen
  repo (`src/neoag/open_neo/cli.py`, `configs/workflows/
  production_workflow.example.toml`, `controlled_execution/gateway.py`)
  with per-row source citations; the UI exposes them progressively
  instead of a thin free-text form.
- **Input selection by description**: the user describes where data
  live in natural language; the agent proposes an input manifest;
  the user reviews/corrects/accepts; the accepted manifest rides on
  the job (`requested_config` is validated, persisted and surfaced
  in results provenance).
- **Job classification**: analysis jobs vs discovery jobs are
  separate kinds (`kind=analysis|discovery`), so conversational
  research/inspection activities never mutate formal analysis
  records; audit rows are append-only.
- **Autonomous vs Controlled modes preserved**, including decision
  history (options, chosen action, rationale, evidence, policy id +
  version, decided_by), mid-run mode switching at stage boundaries,
  bounded failure recovery (one retry, then stop) and skip-essential
  marking `production_release=false`.
- **Policies page removed** in favor of a real Help/Documentation
  view (`backend/help_docs.py`): the app guide plus the real repo's
  README and integration docs, rendered read-only.
- **Real-agent chat**: `POST /api/chat` in `real` mode starts an actual
  run on the server-side CodeBuddy gateway and streams what arrives.
  Mock mode (default) stays fully scripted.

## Architecture

```
frontend/  index.html + app.js + styles.css    (vanilla JS, SSE-driven)
backend/
  server.py   HTTP API + SSE + static serving, 127.0.0.1:8712,
              Basic auth on every route
  agent.py    demo agent (scripted intents) + real-agent relay
              (CodeBuddyClient) + manifest proposal
  codebuddy_client.py  minimal authenticated client for the
              CodeBuddy gateway runs API (login, create, status,
              cancel, SSE stream) with bounded retries and
              bounded streaming
  neoag_params.py     code-grounded parameter inventory
              (source-cited rows from the frozen NeoAG repo)
  help_docs.py        Help/Documentation content (app guide,
              real-repo docs, codebuddy integration status)
  jobs.py     mock engine; cooperative pause/cancel at step
              boundaries; dual execution modes with shared
              decision points
  policies.py validated NeoAG policy rules - separate quoted
              channel
  store.py    sqlite: jobs, job_events, messages, approvals,
              audit, settings, decisions, research,
              research_events (+ startup migration that purges
              pre-redesign mock banner rows)
  research.py SOTA tool discovery module - MOCK digests only
  mock_data.py synthetic cases/stages/candidates (seeded)
```

API (all JSON, all behind Basic auth): `GET /api/bootstrap |
/api/params | /api/audit | /api/help | /api/help/<name> |
/api/manifests/<id> | /api/decisions?job_id= | /api/codebuddy/status |
/api/stream (SSE) | /api/jobs/<id>/events | /api/results/<id> |
/api/research/<id>`; `POST /api/chat | /api/agent/mode |
/api/manifests/propose | /api/jobs | /api/jobs/<id>/pause|resume|cancel|
mode | /api/approvals/<id> | /api/decisions/<id>/resolve |
/api/research | /api/settings`.

## Real-agent integration (CodeBuddy gateway) - verified status

The demo talks to the operator's own CodeBuddy Web UI gateway on
127.0.0.1:7890 using the documented runs API. Verified live
2026-11-13:

| Capability | State | Notes |
| --- | --- | --- |
| Login probe (`POST /api/v1/auth/login`) | verified | password read from `~/.codebuddy/settings.json` (`gateway.password`), never logged |
| Run creation (`POST /api/v1/runs`) | verified | 202 + runId; needs `x-codebuddy-request` header; rate-limited (429) after bursts, client backs off 4 x 20 s then reports honestly |
| Run status (`GET /api/v1/runs/<id>`) | verified | 200 + `active` flag |
| Run cancel (`POST .../cancel`) | verified reachable | returns 404 `RUN_NOT_FOUND` for a run that already completed |
| SSE stream (`GET .../stream`) | PARTIAL | connection opens with correct headers, but for the observed runs NO events arrived while active, and completed runs answer 404 (no replay). One successful streamed exchange was observed on 2026-11-12/13; today's runs produced no streamed events within 15-minute windows. |
| Approval relay | NOT implemented | any server-side tool action needing approval must be approved in the operator's own CodeBuddy Web UI; real-mode prompts are restricted to read-only inspection tasks |
| One active run | observed | the client refuses to start a second run while one is active |

Run lifecycle as observed 2026-11-13: a created run sits `active:true`
for roughly 10-15 minutes, then flips to `active:false`; during the
active window the stream endpoint holds the connection open without
sending response headers; after the run leaves the registry, the
stream answers 404. The relay therefore never blocks indefinitely:
short probe timeouts, status re-polls, and explicit end-of-stream
notes ("finished without streamed content - check the operator's
CodeBuddy Web UI") - the chat never fabricates a transcript.

Safety posture of the integration (unchanged):

- Real mode is OFF by default; switching is explicit, audited and
  visible in the UI mode indicator.
- No approval-relay endpoint exists, so the interface never issues
  tool-execution grants; nothing in this integration silently
  enables unrestricted command execution.
- The gateway password is read at client construction from
  `~/.codebuddy/settings.json` and never logged, echoed or stored
  in demo state.

## Security posture (2026-11-13)

- Loopback bind: server listens on 127.0.0.1:8712 only.
- Every route (static files, API, SSE) requires HTTP Basic auth.
  Credentials live in `data/auth.json` (mode 0600, user
  `operator`). Rotation = delete the file and restart.
- Second, dedicated tunnel for the demo (separate from the
  CodeBuddy UI tunnel on 7890): `TUNNEL_SUFFIX=-demo start_tunnel.sh` /
  `TUNNEL_SUFFIX=-demo stop_tunnel.sh` in
  `/data1/neoag/agents/remote_access`, isolated pidfile and log.
  Quick-tunnel URLs rotate on restart.
- Active gate: Basic auth only. The optional Cloudflare Access email
  layer failed on this host because the system clock runs ~36 s
  behind (NTP disabled); re-enable after an NTP fix (see
  OPERATOR_CHECKLIST.md in remote_access).
- No secrets, no real paths, no patient identifiers anywhere in
  this tree; prototype sqlite state is 0600 by convention.
- pidfiles (`server.pid`, `watchdog.pid`) are gitignored.

## Known risks and next integration tasks

- Gateway runs API is the operator's privileged session: real mode
  must stay opt-in, audited, and read-only in scope until an approval
  relay exists.
- No replay: once a run leaves the gateway registry, its output is
  only in the operator's CodeBuddy Web UI transcript; the demo chat
  cannot recover it (documented, not worked around).
- Quick-tunnel URLs rotate; re-check after restarts.
- Real pipeline execution remains out of scope for this prototype:
  the future path is the NeoAG controlled-execution gateway
  (`/open/run`, job-status, audit files) with a progress reader for
  `production_stage_status.tsv` / `provenance.json`, and a results
  adapter keeping the disclaimer and partial-evidence labels.
