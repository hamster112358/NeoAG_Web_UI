# NeoAG Web UI - conversational front end to the NeoAG neoantigen
# pipeline (MOCK PIPELINE DATA; real-agent chat that EXECUTES under an
# enforced destructive-operation gate, behind an explicit mode switch)

Redesigned 2026-11-13 from a single-page mock prototype into a
conversational shell; redesigned again 2026-11-16 (phase B): ChatGPT-
style conversation persistence, an executing real agent guarded by a
PreToolUse enforcement gate, a clean empty-by-default workspace and a
full-height three-pane layout. Milestone 4 (2026-11-16): honest
output-artifact contract with outcome taxonomy and immutable run
snapshots, decisions that verifiably change outputs, an agent task-
query API, a Skills workspace, and a REAL SOTA discovery engine
(genuine public-source retrieval with persisted query provenance).
Milestone 5 (2026-11-16): ONE execution system behind both interfaces
- enforceable formal-job routing (gate + native adapter + benchmark
jobs), four-concern scientific config, gate-enforced dataset consent,
discovery upgraded into a version-verified / coverage-accounted
decision system with compatibility + adoption-plan actions, and
content-hash-pinned downloadable evidence (HTML/JSON/TSV/PDF +
scoped results bundles).

**Nothing here touches the real pipeline, real data or patient data.**
Every sample ID is `DEMO-*`, every number is generated by a seeded RNG,
and every log line is marked `(mock)`. The real NeoAG repository, the
deployed pipeline, the CodeBuddy Web UI and the Cloudflare tunnel were
NOT modified by this project.

## Run it

```bash
cd /data1/neoag/agents/neoag-web-demo
./start.sh            # -> http://127.0.0.1:8712   (loopback only)
./stop.sh
```

`start.sh` first deploys `agent_workspace_assets/` (the gate hook, the
operations skill and the workspace rules) into the live agent
workspace `/data1/neoag/agents/neoag_agent_ws` - runtime dirs
(`jobs/`, `audit/`, `.neoag-approvals/`) are never removed. Then the
server runs detached under `watchdog.sh` (auto-restart). Durable
state: `data/state.sqlite3`; logs: `data/server.log`.
Stack: Python 3 stdlib only plus a build-free vanilla-JS frontend.

Environment overrides used by the verification suites:
`NEOAG_DEMO_DB` (alternate database file inside `data/`),
`NEOAG_DEMO_PORT`, `NEOAG_SKILLS_DIR` (where seed skills deploy) and
`NEOAG_TASKQ_DIR` (where the task-query token + helper land). Every
suite spawns its own isolated server with throwaway skill/taskq dirs,
so the live demo DB, the live agent workspace skills and the live
`.taskquery-token` are never touched by tests (a fresh-DB server
would otherwise regenerate the token and lock out live agents).

Push transport on this host: system DNS is poisoned for github.com,
so pushes go through a localhost CONNECT proxy pinning github.com to
a known-good GitHub IP, with a retry loop - mid-transfer resets
("Proxy CONNECT aborted", GnuTLS -110) are transient; a successful
push has needed up to 10 attempts. Credentials come from the saved
askpass helper, and the remote is addressed by explicit URL.

## Layout (phase B)

Three panes, the app filling the viewport exactly - the page itself
never scrolls; the sidebar, chat log, workspace body and the job
drawer each scroll independently, and the composer is pinned to the
bottom of the chat pane. The chat pane is resizable (drag the bar;
persisted in localStorage).

- **Left - chat history**: New chat, per-chat title (auto-generated
  from the first message, rename via the pencil or double-click),
  relative time + message count, delete (soft: hidden here, rows
  retained on the server for audit/retention).
- **Middle - the conversation**: one server-saved chat at a time.
  Chats survive restarts; reopening a chat whose live agent session
  is still attached continues it; if the session expired, the next
  message dispatches a fresh agent rebuilt from the saved history and
  the chat shows an honest "session is new" notice - never fake
  continuity. Confirmation cards for blocked destructive operations
  appear inline. An empty chat offers one action: Load Example.
- **Right - workspace**: Tasks (journey-ordered: before you start ->
  prepare -> running & recent, with Task History demoted to a
  collapsible secondary section and an attention strip listing
  everything blocked on a human click), Results, Discovery, Help.

Fresh workspaces start EMPTY (no seeded demo content). Prior
developer records were archived reversibly via
`POST /api/admin/archive` (full row dumps in `data/archive-<ts>.json`,
0600, restorable via `POST /api/admin/restore {"file": "..."}` - the
restore endpoint only accepts archive filenames inside `data/`).

Conversations and formal analysis runs stay separate: chat agent
gateway jobs never enter Task History, and job events never appear as
chat messages.

## Agent execution model (the part that matters)

Real mode connects the chat to a genuine server-side CodeBuddy agent
that EXECUTES. No repeated approval prompts for ordinary work, and no
silent destructive operations either:

- Skill + rules layer (advisory): `CODEBUDDY.md` and the
  `neoag-operations` skill in the agent workspace teach the agent when
  to act, when to ask, the six-item destructive-op explanation,
  bounded retries and provenance recording (`decisions.jsonl`).
  Advisory alone is not enforcement - see below.
- Enforcement layer (technical): the agent workspace installs a
  PreToolUse hook (`.codebuddy/gate.py`, versioned here in
  `agent_workspace_assets/`) that fires before EVERY tool call of the
  dispatched job, outside the model's control:

  | class | examples | outcome |
  | --- | --- | --- |
  | ALLOW | reads anywhere; writes + routine `rm` inside the workspace, `/tmp`, the job-output root | executes, no prompt, audit-logged |
  | DENY (no approval path) | credential/config paths (`~/.codebuddy`, ssh keys, `auth.json`, the secrets dir), the gate's own files, writes into frozen operator trees | blocked always |
  | CONFIRM | deletes outside scratch roots, writes outside roots, force/system verbs (sudo, kill, chmod -R, git push --force, dd, services) | blocked until a single-use human grant |

- A CONFIRM denial answers `NEOAG_CONFIRM_REQUIRED op=<sha256:24>`;
  the backend turns it into a confirmation card in the chat and the
  agent explains exact path / what changes / reversibility / backup /
  why necessary / safer alternative. Approving the card writes a
  single-use grant file (TTL 10 min, 0600) keyed by the hash of the
  EXACT tool+command; the gate consumes it on an identical retry -
  one unlock, one operation. A paraphrased command hashes differently
  and needs its own card. Denials and grants are recorded in
  `audit/exec.jsonl` and the app audit table.
- The workspace lives OUTSIDE any git repo on purpose: jobs dispatched
  inside a repo run in `.codebuddy/worktrees/bg-<id>` copies where
  project settings (and therefore the gate) would not apply. Measured.
- Honest limitation: the agent runs as the same OS user as the gate,
  so this stops realistic failure modes (model mistakes, misread
  instructions, ambiguous requests), not deliberately hostile code.

Autonomous vs Controlled (formal runs, unchanged semantics, clearer
wording in the UI): Controlled pauses at each decision point and asks;
Autonomous applies each decision's POLICY DEFAULT - a documented
default, explicitly labelled as not scientifically validated - and
records every choice with its policy id + version. Both still need
one human approval before execute-class work starts, and the gate
above applies to the real agent regardless of mode.

## Workflow reliability contract (milestone 4)

- **Formalized decisions.** The three pipeline decision points (RNA
  input mapping, stability gate, ranking outputs) carry stable keys,
  category, trigger, policy id + version, mandatory flag, effect
  class, source, and an explicit option -> execution mapping the
  engine really applies. `validated: true` is gone; options carry
  `policy_default` + an honest `validation_status` string.
- **Decisions change outputs, provably.** Chosen options map to
  execution: weighted-only produces exactly one artifact; both
  produces two distinct tables; gate20 vs gate14 changes which
  candidates pass, flips `production_release` warnings, and lands in
  the run's effective config + warnings. Regression-covered per
  choice (battery checks 70-74).
- **Artifact manifest + honest outcome.** Every formal run writes an
  artifact manifest; Results rebuilds from the live artifacts table
  and classifies the outcome: delivered / zero_candidates / partial /
  generation_failed / no_artifacts. A completed lifecycle state can
  still be NOT deliverable; deleted or empty artifacts after the fact
  produce visible outcome drift and a downgrade (check 78), never a
  silent success.
- **Immutable snapshots.** At start each run writes a write-once
  effective-config snapshot (engine/policy/dataset versions, seed,
  stage plan, requested config, decision definitions) reachable at
  `/api/tasks/<id>/snapshot`; INSERT OR IGNORE - it is never updated
  retroactively.

## Agent task-query API (B1/B2)

`GET /api/tasks`, `/api/tasks/active?conv_id=`, `/api/tasks/<id>`,
`/api/tasks/<id>/snapshot`, `/api/research(+events)` - the same
backend the UI uses, no ad-hoc SQL. Chat agents authenticate with a
per-install token (header `X-NeoAG-Task-Token`, file
`.taskquery-token` 0600 in the agent workspace, deployed at startup):
GET-only, scoped to task-query prefixes; it cannot reach bootstrap,
conversations or any POST (verified both directions). Conversation
linkage is persisted on every job/research task; ambiguous ownership
answers honestly (no conv_id -> no guesses, never "most recent").

## Skills workspace (C)

Skills tab: list/read/create/edit/enable-disable, version history
with restore, structural test, and deploy into the agent workspace
via the CodeBuddy-native skill mechanism. Three seeded categories
(NeoAG Operation / NeoAG Web Awareness / Scientific Evidence &
Research) reuse the instructions written in earlier milestones.
Activation is honest: `active_in_new_sessions` compares the deployed
copy byte-for-byte with the saved draft, so "edited but not
deployed" is visible; skills apply to NEW agent sessions only, and
skills are ADVISORY - gate/policies/thresholds stay enforced outside
them and are not editable through skills (a skill that ships gate
edits is refused at validation).

## Real SOTA discovery (D)

Two engines, clearly separated in UI and storage:

- **live** (default): real HTTP retrieval through no-credential
  adapters for Europe PMC, PubMed, OpenAlex, GitHub, bio.tools,
  PyPI. Flow: scope -> code-grounded inventory (backend/inventory.py
  reads the frozen repo: 13 stages, tools with exact pinned versions,
  git commit) -> multi-query literature + software retrieval per
  target -> candidate verification -> comparison across a fixed
  field set (D5 schema; unverifiable fields print "Not verified")
  -> task-specific metrics with explicit comparability warnings
  (never rank across incomparable AUCs) -> fully-sourced next steps.
  Every attempt persists provenance: queries, per-source counts,
  dedup, exclusions + reasons, failures. Unreachable sources make the
  report honestly incomplete, not fake.
  Candidate names come only from the configured workflow, GitHub
  task-search hits, and tool-shaped words in retrieved titles
  (internal capitals or a digit; generic scholarly words are
  stoplisted) - and a registry record counts as evidence only when
  it is actually named after the candidate, so a same-named
  unrelated repo can never misattribute a license.
- **example**: the old fixture, badged as an example everywhere;
  live reports assert at generation time that no mock content leaked
  in ("NO tool was executed" disclaimer lives in the example engine
  only).

Research jobs are durable: progress steps persist, cancel is
cooperative, resume after restart works, and chat requests create
tasks through the SAME `/api/research` workflow the UI uses.

## One execution system, two interfaces (milestone 5)

Chat, GUI and task-token all submit into the SAME job system: one
record, the same human approval card, the same Task History entry, the
same artifact ledger and outcome taxonomy. What differs is only who
pressed the button.

- **Formal-job routing is enforceable, not prose.** The deployed
  PreToolUse gate classifies raw pipeline launches (`open-neo run
  --mode execute`, `neoag.cli run*`, direct gateway posts, ad-hoc
  gateway launches) as DENY-FORMAL: no approval path - the agent must
  REGISTER the work via `.neoag/taskquery.py job submit`, which
  produces exactly the GUI's task behind the GUI's approval card.
  Planning/inspection (`--mode plan`, doctor, reads) stays free;
  every interception is audit-logged (`.neoag-approvals/
  routing.jsonl`). Native engine: `backend/native.py` wraps the real
  NeoAG packages READ-ONLY (probe / run_plan / preview execute
  nothing and never patch tools); a native run executes only as a
  formal job on an approved, version-pinned profile.
- **Scientific config is split into four concerns** (algorithm
  weights, workflow routes, evaluation thresholds, output controls)
  so a config choice on the card states what class of thing it
  changes; requested vs effective config both persist per run, and
  the demo control panel writes ONLY whitelisted UI keys - it can
  never touch the task token or any stored setting (battery 127).
- **Dataset consent is enforced, not suggested** (PART 3): literature
  reads stay free; a download-class command raises a structured
  consent card (dataset / operation / bounded resource scope /
  destination / job), and approval writes a 72 h scope grant for
  THAT source -> THAT destination only. Benchmark jobs apply the
  same rule to their input: the synthetic demo fixture is free, any
  other dataset needs an APPROVED dataset-download consent card
  naming that dataset - free prose mentioning "dataset" (even an
  approved benchmark card) does not count, and benchmarks never
  download anything at run time.
- **Discovery became a decision system** (PART 4): per-candidate
  version-verification chains (tags -> releases -> development
  commit, each step labelled); performance numbers are context-gated
  (metric + dataset + tool version or the number is quoted but
  excluded, cross-version credit is blocked); conclusions use a fixed
  vocabulary with a five-part explanation (evidence / advantage /
  comparability / usability / remaining verification) and can never
  invent a winner from one-sided evidence; every inventory module's
  retrieval COVERAGE is accounted (researched vs thin vs missing +
  reason); a stopped run publishes no premature conclusions.
  Follow-up actions derive ONLY from the stored report:
  `/api/research/<rid>/compatibility` probes presence/version/license
  on this host and states its interface is NOT verified;
  `/api/research/<rid>/adoption-plan` writes a 7-step plan, marks the
  honest kind (config tool-slot vs code-integration change) and
  APPLIES nothing; a candidate the report never retrieved is a 404,
  never an invented row (battery 119).
- **Benchmarks are formal experiments** (PART 6): the approval card
  carries the full brief (hypothesis, tools, baseline, metrics,
  compute estimate, risks, dataset + consent). After approval the
  harness runs the deployment's own ranking strategies for real on
  IDENTICAL seeded pools and COMPUTES paired metrics from the
  produced tables (top-k overlap, Spearman over shared items, Jaccard
  set fraction - nulls stated, never substituted); an external tool
  not installed here gets a reviewable RUN PLAN arm and its metrics
  stay explicitly UNANSWERED. Every run persists a reproducibility
  record (seed, input-pool sha256, environment, measured wall time,
  tool probes) and an honest ground-truth statement ("identical-
  input property, NOT validated biology"). Deny kills it before
  anything runs (battery 116-121 + E2E).
- **Downloadable evidence is render-once-serve-forever** (PART 7):
  report exports (standalone decision-first HTML, full JSON with the
  export envelope, sectioned TSV, and a stdlib text-only PDF) plus
  per-run results bundles are persisted files pinned by content hash
  - re-downloads serve byte-identical bytes, and a new version row
  appears only when the stored content actually changes (never a
  regeneration, never a re-run). Bundles ship persisted DB state
  (job, result, immutable snapshot, decisions, artifacts, events,
  ranking tables) plus real native/benchmark run-output files under
  `native/` - native-generated HTML reports travel inside the bundle
  - while raw FASTQ/BAM-class inputs and oversized files are excluded
  with the exclusion recorded in the manifest. Downloads sit behind
  the same Basic auth; the read-only task token may GET them and can
  never POST; a non-completed run is refused (409) rather than
  generated on demand.

Status split, honestly: native execution exists and plans/previews
for real, but runs only against synthetic demo inputs; real-pipeline
execution on real data remains out of scope by design; the PDF
export is text-only by construction (12-page cap, truncation
disclosed); browser acceptance stays with the operator (no browser
tooling on this host).

## Scientific research quality & unified entry (milestone 6)

Driven by the 2026-11-17 research report as a NEGATIVE test fixture:
what that report got wrong is what this milestone changed.

- **Relevance is decided by generalizable scientific rules, never by
  name lists** (A1/A2). A candidate enters a comparison only if its own
  retrieved text describes performing the module's task (per-module
  TASK_PROFILES + domain anchors); baselines are labelled
  `current baseline (not an alternative)`, wrappers/complementary/
  unrelated/insufficient each get an explicit six-class eligibility
  verdict WITH a reason recorded in provenance; the intro-cue
  privilege belongs to the one name a publication introduces, and
  allele/virus-shaped names cannot be minted as tools (battery 138,
  discovery checks 28-32).
- **Baselines are identified from the deployed code** (A3): the
  code-grounded inventory names, per module, the tools the workflow
  TOML + planner wiring + conda pins actually run, with file:line
  evidence - a baseline candidate can never be scored as an external
  alternative.
- **Literature-first, evidence-record-per-number** (A4/A6): tool names
  are EXTRACTED from retrieved titles/abstracts under shape guards and
  closed-class stop-rules (institutions and connectives cannot mint
  candidates), deduplicated by DOI/PMID/PMCID, and a performance
  number counts only with metric + dataset + tool version
  (A6/A8: rate-limit waits and definite registry-absence answers are
  recorded outcomes of the version chain - tagged in provenance and
  never silently demoting a module; discovery check 34).
- **Recommendations can never outrun evidence** (A9/A10): a pure
  `recommend()` over the stored rows, superiority only from same-
  metric same-dataset paired comparisons, quality gates decide
  `decision_ready`, and a targeted run is "complete for its scope"
  instead of faking full-pipeline verdicts.
- **Conclusion-first reports** (B): 1. Executive assessment (readable
  in about a minute) / 2. Module-level recommendations / 3. Per-module
  scientific comparison / 4. Priority actions / 5. collapsed technical
  appendix - identical structure in HTML, PDF and in-browser, light +
  dark via CSS variables, full provenance in JSON/TSV, exports pinned
  by content hash.
- **Benchmark consent is a complete, backend-enforced experiment
  proposal** (C): nine mandatory fields (dataset+source, question,
  comparison tools, download size, storage destination, compute,
  metrics, installation, NeoAG-modification flag - the last must be
  false), and the user answers APPROVE / REJECT / LIMIT SCOPE (re-
  scope on a fresh card) / LITERATURE ONLY; every non-approve answer
  cancels the formal job with its own recorded reason (battery
  128-130).
- **One native entry** (D): a data directory is the whole request - a
  read-only scan maps files to real `open-neo run` flags (contents
  never opened, ambiguity surfaced not guessed), the CONFIRMED
  manifest is authoritative input, the native planner decides branches,
  and Chat/Tasks submissions land in the same unified job backend
  (battery 131-133).
- **Scientific configuration is a small verified structured set** (E):
  fixed-choice radios, bounded numbers and checkboxes only - every
  control cites the deployed code, is re-validated server-side
  (choices/ranges/booleans), forwards to real execution, and stays at
  the native default until touched; decisions the deployed code makes
  on its own (presentation consensus, LOH/CCF scoring, fusion caps)
  are documented with file:line citations instead of fake knobs
  (battery 134-135).
- **Chat/UI reliability** (F): conversation ellipsis menu (rename /
  pin / archive / unarchive / delete), the header rename and native
  confirms are gone, the agent-mode switch is an explanatory dropdown
  that the BACKEND refuses while a chat turn or job is in flight
  (battery 136-137), the prep text lives in Help, and known-cause
  errors get concise answers per the workspace rules instead of
  minutes of tool churn.

## Real-agent integration (CodeBuddy gateway Jobs API) - verified

Gateway on 127.0.0.1:7890, v2.180.0, measured (not assumed):

| Capability | State | Notes |
| --- | --- | --- |
| Dispatch (`POST /api/v1/jobs`, default permission mode) | verified | dispatched jobs AUTO-EXECUTE tools (headless workers have no interactive approval; an "ask" decision auto-denies) - which is why safety is enforced by the workspace gate, not gateway prompts |
| Plan mode | measured | execution tools denied verbatim; used only as evidence, this app does NOT run chats in plan mode anymore |
| Lifecycle / transcript / reply | verified | `data.job` states; one-shot ACP transcript replay as the reliable content channel; `reply` continues the SAME session after settle (multi-turn) |
| Reattach after demo restart | verified E2E | job id persisted on the conversation; while alive the next message continues the same session (no "new session" notice) |
| Expired-session recovery | verified E2E | job gone -> fresh dispatch rebuilt from durable saved history + honest "session is new" notice; earlier facts recalled |
| Gate E2E | verified E2E | routine write executes silently; outside-workspace write blocked -> card -> approve -> identical retry executes (grant consumed); credential-path read blocked with NO card, secret never observed in any transcript |
| Rate limits / quirks | handled | 429 backoff; lenient JSON (`strict=False`) for raw newlines; ids not names; settled jobs need `?all=1` |

Relay: the backend polls the transcript every 2.5 s (900 s cap),
posts tool activity live, delivers the newest assistant message once
at settle (already-delivered messages are never re-sent), and posts
an honest turn-end note when the gateway recorded no reply.
The workspace never fabricates agent output.

### Turn delivery and honest terminal states (2026-11-16 fix)

Field failure: through the Cloudflare quick tunnel the browser
received NO SSE bytes - the tunnel buffers streaming responses
(proved: localhost SSE delivered instantly; via tunnel zero bytes in
40 s; the tunnel log shows `context canceled` every ~2 min). Real
replies were relayed and stored server-side within seconds, but the
UI depended solely on SSE, so chats appeared stuck in "streaming" -
and the kickoff notice's `streaming` badge was persisted and never
cleared, so even a reload looked stalled.

Fixes (verified: live 12/12 + battery 64-68 + real-mode R7/R8):

- Every turn ends in a PERSISTED terminal `turn_state` stamped onto
  its kickoff message: completed / failed / cancelled /
  no reply recorded / timed out / connection lost / relay error;
  a server restart mid-turn sweeps orphans to
  "interrupted by server restart". No path leaves a message
  streaming forever.
- The relay tolerates transient gateway blips (3 retries), then says
  honestly that the job connection was lost - never a guess.
- Frontend never trusts SSE: it refetches on every SSE (re)open and
  polls every 3 s while the visible chat shows a streaming turn, so
  the terminal state arrives whatever the proxy does.
- The "previous agent session had ended" recovery notice now appears
  only when a real session actually existed for that chat (not on a
  fresh chat that merely has mock-era history).

## Security posture

- Loopback bind; Basic auth on every route; credentials in
  `data/auth.json` (0600). Rotation = delete file + restart. Demo
  tunnel: `TUNNEL_SUFFIX=-demo` scripts in `/data1/neoag/agents/
  remote_access` (URLs rotate).
- Real mode OFF by default, explicit audited switch.
- Credential/config paths are unreachable to the agent (deny, no
  approval path); the gate protects itself and frozen operator trees;
  grants are single-use, hash-matched, TTL-bound, 0600.
- Gateway password read from `~/.codebuddy/settings.json` at client
  construction; never logged or stored in demo state.
- No secrets, real paths or patient identifiers in this tree.

## Known risks / limits

- SSE does not survive the quick tunnel (buffered): live updates
  there arrive via the 3 s watchdog instead of instantly. The fix
  is delivery-agnostic; a future tunnel protocol tweak may restore
  instant push.
- Same-uid: the gate defends against mistakes, not hostile code
  running as the same user.
- One in-flight exchange per chat; rate-limited dispatch; transcript
  window is bounded (~1000 lines) - very long chats relay the tail.
- Deleted chats are soft-deleted (retained); hard purge is a
  deliberate future operator action, not automated.
- Real pipeline execution stays out of scope; formal runs go through
  the demo's approval queue as before.
- Shared-workspace session replay: gateway sessions keyed by the
  workspace cwd can carry an EARLIER run's consented-but-unexecuted
  action into a later fresh conversation; the gate re-blocks it
  (grants are single-use), but a real-mode test expecting a fully
  quiet turn may still see that card. Per-run workspace isolation
  for the suites would drain this; left as a known test-environment
  flake, not a product gap.
- Benchmark metrics are computed for real but on a SMALL seeded
  synthetic pool (top_n ~12): values legitimately vary per seed and
  the consensus arm can lawfully produce an empty table - the result
  then states the stated metrics are UNANSWERED; no number is ever
  substituted to make a run look complete.
- PDF export is text-only by construction (no figures, 12-page cap
  with an explicit truncation line); full detail travels in the
  HTML/JSON exports and the results bundle.
