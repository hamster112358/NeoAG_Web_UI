# NeoAG Web Demo - conversational UI prototype (MOCK DATA ONLY)

Standalone prototype for a non-technical-user front end to the NeoAG
neoantigen pipeline. Milestone 1 built and verified 2026-11-13; milestone 2
(SOTA tool discovery, dual execution modes, persistent decision history)
extended and verified the same day.

**Nothing here touches the real pipeline, real data or patient data.**
Every sample ID is `DEMO-*`, every number is generated by a seeded RNG, and
every log line is marked `(mock)`. The real NeoAG repository, the deployed
pipeline, the CodeBuddy Web UI and the Cloudflare tunnel were NOT modified
by this project.

## Run it

```bash
cd /data1/neoag/agents/neoag-web-demo
./start.sh            # -> http://127.0.0.1:8712   (loopback only)
./stop.sh
```

Server log / durable state: `data/server.log`, `data/state.sqlite3`.
Stack: Python 3 stdlib only (`ThreadingHTTPServer`, `sqlite3`) + a
build-free vanilla-JS frontend. No packages installed anywhere.

## Architecture

```
frontend/  index.html + app.js + styles.css    (vanilla JS, SSE-driven)
backend/
  server.py   HTTP API + SSE + static serving, 127.0.0.1:8712
  agent.py    scripted demo agent (no LLM) - strict suggestion channel
  policies.py validated NeoAG policy rules - separate quoted channel
  jobs.py     mock engine; cooperative pause/cancel at step boundaries;
              dual execution modes (autonomous/controlled) with shared
              decision points and a persistent decision history
  store.py    sqlite: jobs, job_events, messages, approvals, audit,
              settings, decisions, research, research_events
  research.py SOTA tool discovery module - MOCK digests only (static
              hand-written example content, no network access)
  mock_data.py synthetic cases/stages/candidates (seeded, reproducible)
```

API (all JSON): `GET /api/bootstrap | /api/audit | /api/stream (SSE) |
/api/jobs/<id>/events | /api/results/<id> | /api/research/<id>`; `POST
/api/chat | /api/jobs | /api/jobs/<id>/pause|resume|cancel|mode |
/api/approvals/<id> | /api/decisions/<id>/resolve | /api/research |
/api/settings`.

Key invariants encoded in code, not just docs:
- **Policy vs suggestion separation**: chat messages carry role+badge -
  `policy` messages are verbatim quotes from `policies.py` with repo
  sources; `agent` messages are always badged "agent suggestion".
- **Predictions are never presented as validated**: results carry a
  persistent disclaimer banner (README "Important boundary", POL-002) and
  per-candidate provenance (job id, seed, engine=mock, dataset version).
- **Approval boundaries**: every execute-class request lands `blocked`
  with a pending approval (mirrors gateway POL-005 `approved=true` rule);
  deny cancels. File preview/download: not implemented, labelled as such -
  no path exists for agent or UI to read real files.
- **Durable job states**: queued/running/paused/blocked/completed/failed/
  cancelled persisted before the worker reacts; a server restart marks
  in-flight jobs `failed: interrupted by server restart` (visible, audited).
- **Genuine cancellation**: the worker checks the cancel flag at every
  substep; partial work is discarded and the event recorded. Pause/resume
  act on the worker, not on chat rendering.
- **Audit trail**: every user/agent/engine action appends to `audit`.

## Milestone 2: execution modes, decision history, SOTA discovery

**Dual execution modes** (same engine, same validity gates, only WHO
resolves a decision point differs):

- `controlled` (default): the run blocks at each decision point
  (input mapping, stability-gate parameter, ranking outputs, stage
  failure) and shows option cards; the user's choice is recorded with
  decided_by=user.
- `autonomous`: the engine auto-resolves each decision point to the
  validated default and records the choice (decided_by=engine,
  rationale cites the default); failure recovery is bounded to ONE
  automatic retry, then the run STOPS with a failed status and an explicit
  reason - it never silently skips an essential stage.
- **Mode switching** mid-run is requested from the job card and applies
  at the next stage boundary; it is recorded as a `mode_switch` decision
  (decided_by=user). A decision already pending when the switch is
  requested still needs an answer.
- **Skip is never silent**: skipping an essential stage (e.g. after a
  failure, user chooses skip over retry) is possible only as an explicit
  recorded decision and marks the run `production_release=false` with a
  release note naming the skipped stage.
- **Approval boundary holds in BOTH modes**: approval-for-execute is a
  policy invariant, not a mode setting; autonomy never bypasses it.

**Persistent decision history** (`decisions` table + Decisions panel):

Every decision stores timestamp, job, stage, decision type, the options
considered (with validated/alternative flags), the chosen action,
rationale, evidence, policy id + policy version, who decided
(user/engine) and status (pending/resolved/cancelled). It is inspectable
during and after execution; it survives server restarts (sqlite). The
audit trail separately records every resolution event.

**SOTA Tool Discovery & Benchmarking module** (Discovery panel):

- Scope: full pipeline review or a targeted review (presentation,
  stability, fusion discovery, HLA typing).
- Comparison rows carry: tool + version, availability class
  (open-source | freely available with restrictions | license-required
  | commercial | unavailable | unclear), license, source citation,
  publication year, evidence quality, example accuracy/performance
  figures, I/O compatibility, maintenance, notes.
- Every row is labelled `basis: literature-derived (MOCK digest ...)` and
  `independently_benchmarked: False` - the separation between
  literature-derived claims and independently benchmarked results is
  enforced in the data model, not just in prose.
- Output: a recommendation that currently concludes "No replacement
  recommended from this mock digest", plus a 5-step pre-adoption
  experiment list (reproduce on own validation fixture, A/B on demo
  cases, license review, version pinning, output-schema check).
- **No live research is connected**: no literature search, no downloads,
  no benchmarking. When a real research adapter exists, it fills the
  same report shape.

## NeoAG real integration points (read-only inspection, 2026-11-13)

Repo: `/data2/caojingqi/original_OpenNeoAG/neoag` (frozen original; dev tree
diverges only in our audited fixes).

- **CLI entry** `open-neo` = `python -m neoag.open_neo.cli` with exactly
  three subcommands: `install-check` (Skill1), `run` (Skill2: input QC,
  routing, execute/resume), `review` (Skill3: read-only reports).
- **Controlled-execution gateway** `python -m neoag.controlled_execution.gateway`
  (`src/neoag/controlled_execution/gateway.py`): stdlib HTTP server designed
  for `--host 127.0.0.1`; routes `/health`, `GET /job-status/<id>`, POST
  `/doctor /input-qc /ranking-compare /appm-review /ccf-review
  /patient-report /pipeline-full /open/install-check /open/run /open/review`.
  Risk tiers LOW/MEDIUM/HIGH computed per request (`_risk`); HIGH without
  `approved=true` answers `403 APPROVAL_REQUIRED` (job recorded, nothing
  runs). Write paths fenced by `--allowed-root`; install/delete flags
  refused (`UNSUPPORTED_HIGH_RISK_ACTION`). Per-job artifacts:
  `request.json, approval.json, job_status.json, audit_log.jsonl`.
- **Real-run submit** the prototype will mirror: `open-neo run
  --sample-manifest ... --mode execute --approved --gateway-url
  http://127.0.0.1:8000 --gateway-wait`; resume via `--result-dir --mode
  resume`. Dry-run is the default everywhere (POL-007).
- **Stages** (`configs/workflows/production_workflow.example.toml` +
  `docs/PRODUCTION_WORKFLOW.md`): hla_typing, purity_cnv, hla_loh,
  rna_expression, snv, fusion_discovery/peptides, splice_discovery/peptides
  -> unified presentation (NetMHCpan/MHCflurry/NetMHCstabpan/NetChop),
  safety+escape, weighted+evidence-consensus ranking, reports. The demo
  stage list mirrors these names.
- **Stage status/audit on disk**: `production_stage_status.tsv`,
  `provenance.json`, `manifests/` under the run's output dir - the future
  progress reader should parse these.
- **Reports**: `open-neo review --reports patient,technical,onepage`.
- **LLM agent** already exists in-repo: `bin/neoag-llm-agent` ->
  `neoag.llm_coordinator.coordinator_agent` (conda env `neoag-vllm`).
- **Gateway gap**: it has no cancel/pause/kill endpoint and no SSE log
  stream. `--gateway-wait` polls; real cancellation must be added
  (SIGTERM of the stage subprocess group) before the UI can promise
  "stop" for real runs.

## CodeBuddy reuse decision (milestone 1)

**Not reused.** CodeBuddy's gateway API (`POST /api/v1/auth/login`, `POST
/api/v1/runs`, SSE `/api/v1/runs/<id>/stream` - all verified live) is the
*operator's privileged session*: reusing it would share the operator
password/cookie, inherit real tool access and bypass this app's approval
model, and violate the separation requirement. The demo agent is scripted.
Future option (separate review needed): a dedicated CodeBuddy serve
instance with its own password + a non-default permission mode, or the
in-repo `neoag.llm_coordinator`.

## Security posture (updated for milestone 2.5, 2026-11-13)

- Loopback bind unchanged: server listens on 127.0.0.1:8712 only.
- **Application-level auth is now implemented**: every route
  (static files, API, SSE) requires HTTP Basic auth. Credentials live in
  `data/auth.json` (mode 0600, user `operator`). Rotation = delete the
  file and restart; a new password is generated. The password value is
  never printed to chat or logs.
- **Second, dedicated tunnel for the demo** (separate from the CodeBuddy
  UI tunnel on 7890): `TUNNEL_SUFFIX=-demo start_tunnel.sh` /
  `TUNNEL_SUFFIX=-demo stop_tunnel.sh` in
  `/data1/neoag/agents/remote_access`. It uses isolated pidfile
  (`tunnel-demo.pid`) and log (`logs/tunnel-demo.log`), so the primary
  tunnel is never touched.
- **Active gate: Basic auth only.** An optional Cloudflare Access email
  layer (`--allowed-mail`) was tried first and FAILED on this host: the
  system clock runs ~36 s behind (NTP disabled), so cloudflared rejects
  Cloudflare's signed post-login assertion ("token issued in the
  future (iat)") and the browser gets "Forbidden" even with a correct
  PIN. It can be re-enabled once the admin enables NTP (see
  OPERATOR_CHECKLIST.md in remote_access). Until then: Basic auth +
  URL secrecy. The quick URL is unguessable and the demo is mock-only.
- Order of operations honored: Basic auth verified (401 without /
  with wrong credentials) BEFORE the tunnel was started, and re-verified
  through the public URL after the change (anonymous -> 401 challenge,
  authenticated -> 200).
- Quick-tunnel caveat: the public URL rotates on every tunnel restart.
- No secrets, no real paths (mock file lists are strings), no patient
  identifiers anywhere in this tree.
- Prototype SQLite state holds only synthetic content, but is 0600 by
  project convention anyway.

## Known risks

- Gateway is single-process stdlib HTTP with in-memory job map + JSON
  files: fine loopback, unsafe multi-user (no auth) - keep loopback.
- No real cancel exists today (see task 3) - a hard-killed stage can leave
  Nextflow residue; document for users.
- Mock stage model is simplified (sequential); real DAG runs branches in
  parallel (POL-008) - progress % will not be linear once real.
- Licensed tools (NetMHC* etc.) keep vendor-license constraints; a
  "production" toggle must re-check `PRODUCTION_REQUIRED_TOOLS` before
  submit, not after.
- Mock digests are static hand-written content: availability classes
  and example figures are illustrative and will age - a real adoption
  decision must re-verify each row from primary sources.
- Decision points are stage-boundary only: mid-stage parameter changes
  are not modelled; a real integration needs its own boundary definition.
