# Public access reliability fix - 2026-11-18

Plain-text maintenance report. Current URLs are never stored in this file
or anywhere in Git; `./tunnel-status.sh` is the only authority.

## 1. Root cause of the lost public access

The NeoAG Web quick tunnel (started 2026-11-13) kept running happily
while, on 2026-17-Nov 07:18 UTC, Cloudflare reclaimed its
`*.trycloudflare.com` registration server-side. From that moment every
connection attempt logged `Register tunnel error from server side:
Unauthorized: Tunnel not found`, retried "in up to 32s", forever: quick
mode never re-requests a hostname and never exits. Evidence chain:
process alive but zero established TCP/7844 sockets; the hostname
returned no DNS answer; local `GET 127.0.0.1:8712` answered 401 (the app
was fine). The legacy `start_tunnel.sh` was a one-shot `nohup` launcher -
no supervisor existed for tunnels, so the failure was permanent until
noticed by a human. (The gateway tunnel happened to re-register cleanly
on 2026-11-17 14:46 UTC and stayed healthy, which is why only the web
side went dark.)

## 2. Final topology

```
browser -> quick tunnel #1 (systemd: neoag-tunnel-web.service)
              -> NeoAG Web 127.0.0.1:8712 (Basic auth ON, unchanged)
                    -> CodeBuddy Gateway 127.0.0.1:7890 (loopback,
                       backend/codebuddy_client.py - always has been)

operator browser -> quick tunnel #2 (systemd: neoag-tunnel-gw.service)
              -> Host: localhost:7890 -> CodeBuddy Gateway :7890
```

Two public tunnels, deliberately. Evidence for keeping the second one:
the demo backend reaches the gateway over loopback only, and the
frontend contains no external URLs - the app needs exactly one entry
point. The gateway tunnel's sole client is the operator's browser using
the CodeBuddy chat UI directly, a surface the demo does not proxy (its
browser acceptance is still open). Merging to one tunnel would silently
delete that capability, and the demo cannot proxy it without new Web UI
features, which this task must not add. If that capability is ever
dropped, retiring `neoag-tunnel-gw.service` is one command
(documented in README_TUNNELS.md).

No new ports were opened anywhere; cloudflared is outbound-only over
TCP/7844 (http2: UDP is blocked host-wide). The gateway remains bound to
127.0.0.1; nothing about application authentication changed.

## 3. What was built

User-level systemd (linger enabled 2026-11-18, so recovery survives
reboot/logout):

* `neoag-tunnel-web.service` / `neoag-tunnel-gw.service` - cloudflared in
  the foreground, `Restart=always RestartSec=10`,
  `StartLimitIntervalSec=600 StartLimitBurst=5`, logs appended to
  0600 files under `/data1/neoag/agents/remote_access/tunnels/`.
  `Restart=` alone cannot fix the incident class above (the process
  never exits), hence:
* `neoag-tunnel-health.timer` (every minute) -> one recovery cycle
  (`tunnelctl.py`): five layered probes (unit / app / network /
  edge-connection / public route), failure streaks with grace,
  exponential restart backoff (2 min doubling, 1 h cap, cleared on
  healthy), and the URL handoff contract: a hostname is published in
  `state.json` only after a real end-to-end HTTPS probe, replaced ones
  move to history marked expired.
* `tunnel-status.sh` - the operator command; never shows an expired URL
  as current; exit 0 only when everything is healthy.
* `install_tunnels.sh [--uninstall]` - idempotent installer.

Layer semantics that encode this task's requirements: an app 401 is a
PASS (protected endpoint responding, not an outage); the gateway uses
its designed `GET /health`; with no outbound connectivity or no local
app, NO URL is rotated (rotating can't help and burns the hostname); a
`Tunnel not found` log signature acts immediately, other public failures
need 3 consecutive cycles; an unexpected MainPID change retires the old
hostname after one failed probe (a quick hostname always dies with its
process).

## 6. Remaining limitations (inherited from Quick Tunnel)

* Random hostname rotates on every fresh registration - there is no
  permanent URL and no uptime guarantee; anything bookmarked must be
  refreshed from `tunnel-status.sh` after a recovery event. A Named
  Tunnel (with the operator's Cloudflare account) is the stable-URL
  path; `start_tunnel.sh MODE=named` was written for that future.
* Quick-tunnel creation is rate-limited per source IP: a failure storm
  lengthens recovery (test E: ~5 min, CF-dominated). The backoff keeps
  us under the limiter instead of digging in.
* Edge hostname reclamation is silent for the process; worst-case
  detection latency is one health cycle (~1 min) for the streak path,
  immediate for the log-signature path.
* If the CodeBuddy gateway process itself dies, the supervisor reports
  `upstream-down` and does not rotate a URL that could not serve:
  restarting the gateway (it loads its password at startup) stays an
  operator action, by design - the tunnel supervisor owns only tunnels.

## 7. Rollback

`./install_tunnels.sh --uninstall` removes the supervision entirely.
The legacy manual scheme remains available and unchanged:
`MODE=quick CF_PROTOCOL=http2 TUNNEL_TARGET=<upstream>
[HOST_HEADER=localhost:7890] [TUNNEL_SUFFIX=-demo]
/data1/neoag/agents/remote_access/start_tunnel.sh`. Current units are
git-tracked here under `ops/tunnels/units/`; the live copies are
installed into `~/.config/systemd/user/`.

## ADDENDUM (same day, afternoon): gateway tunnel retired

Sections 2-4 above record the morning state (two tunnels). Later the same
day the operator stated the intended architecture is Browser -> NeoAG
Web -> local Gateway, and that CodeBuddy is used via SSH/tmux and the
demo - so the assumed external client of the gateway tunnel was put to a
dependency audit before any action: no frontend/backend code reference,
no settings/scripts/cron/systemd reference to any gateway public
hostname, zero incoming-request traces on the tunnel, gateway settings
contain no tunnel config, and the operator's tmux sessions are local
PTYs that never touch :7890. Finding: no client exists.

Action: `systemctl --user disable --now neoag-tunnel-gw.service`, unit
removed from the user systemd dir, gw dropped from tunnelctl.py TUNNELS
and install_tunnels.sh (state file auto-prunes the entry; the unit file
stays under units/ for reference). The localhost gateway process was NOT
restarted (pid 686365 unchanged before/after). Post-retirement
verification: /api/codebuddy/status -> connected (gateway v2.180.0) via
loopback AND via the public web URL; conversations endpoint 200; all 8
tmux sessions and long-running CodeBuddy CLI processes untouched; old
gateway public URL now dead (530, then NXDOMAIN). Final topology: one
public tunnel. Along the way one latent defect was fixed: the "app"
layer documents/uses the semantics "any HTTP status = app responding,
only transport failure = down" (the configured app_ok code sets were
never actually consulted - removed as dead config).
